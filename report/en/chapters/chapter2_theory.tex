\chapter{Theoretical Foundations and Core Technologies}
\label{ch:theory}

This chapter introduces the concepts needed to understand the VietForecast web application. It focuses on the data representations and algorithms that support weather lookup, map exploration, and route comparison. Detailed implementation and deployment decisions are discussed in later chapters.

\section{Spatial Data for the Web Application}
VietForecast represents locations and routes using the WGS84 geographic reference system (EPSG:4326) and the GeoJSON format defined by RFC 7946 \cite{rfc7946}. A weather location is represented as a point, a road journey as a LineString, and an administrative area as a polygon. GeoJSON allows the API and the frontend map to exchange these objects using the same structure.

Weather and route data are stored in PostgreSQL with the PostGIS extension \cite{postgis2023}. PostGIS provides spatial types and queries for finding nearby stations, checking whether a point lies within a route corridor, and calculating distances. A GiST spatial index, based on the spatial-tree approach used for indexed search, reduces the number of records that must be examined before an exact distance or intersection check is performed \cite{guttman1984}. This gives the application a practical way to search weather evidence near a route without scanning the complete dataset.

\section{Weather Data and Freshness}
The application uses normalized weather observations and forecasts. Provider-specific condition codes are mapped to a small set of application states, such as clear, cloudy, rain, fog, and thunderstorm. Measurements are kept with their source time and freshness state so that the interface can distinguish current, aging, stale, and unavailable data. The data model follows the general observation principles described by WMO-No. 8 \cite{wmo2021guidelines}.

Freshness is part of the user-facing result. A missing or outdated measurement is reported as unavailable or unknown rather than being silently treated as safe weather. This rule is important for both the weather pages and the route planner because a recommendation is only as reliable as the evidence covering the relevant location and time.

\section{Core Route and Risk Algorithms}
\subsection{Route Sampling with Estimated Arrival Time}
The routing provider returns a road geometry, distance, and estimated duration. Road-network routing and OpenStreetMap-based services provide the underlying route alternatives \cite{haklay2008openstreetmap,luxen2011real,bast2016route}. The application samples the geometry at bounded spatial and temporal intervals. For each checkpoint $p_i$, it estimates an arrival time from the departure time $t_0$ and the distance travelled before that checkpoint:
\begin{equation}
    t_i = t_0 + \sum_{j=1}^{i} \frac{d(p_{j-1},p_j)}{\bar{v}},
\end{equation}
where $\bar{v}$ is the average route speed. The checkpoint location and estimated time are then used to find the weather evidence that is relevant to the vehicle at that point in the journey. This is the main difference between checking weather at the destination and checking weather along a route.

\subsection{Checkpoint Risk Assessment}
Each checkpoint is assessed using the available weather dimensions: rainfall, wind gust, temperature, visibility, storm information, and official alerts. Each dimension is mapped to a simple severity level: Low, Caution, High, or Unknown. The checkpoint level is the highest applicable severity among the available dimensions. If required evidence is missing or stale, the result remains Unknown and the response includes a warning.

The route summary reports the highest checkpoint severity, the proportion of covered checkpoints, and a distance-aware summary of the available evidence. These values are shown together with the warnings and source information so that users can understand both the result and its limitations. The assessment is vehicle-aware: the same weather conditions can produce different warnings for a motorcycle and a car because their exposure and stability differ.

\subsection{Comparing Route Alternatives}
The route planner compares alternatives returned by the routing service, typically labelled Fastest, Shortest, and Weather-Safer. The comparison considers three practical factors:
\begin{itemize}[itemsep=0.25em]
    \item travel time;
    \item route distance; and
    \item weather risk and evidence coverage.
\end{itemize}

The Weather-Safer label is assigned from the application's balanced route score. It is a relative comparison between the available alternatives, not a guarantee that a journey is safe. The interface therefore presents the route geometry, score, warnings, and evidence coverage together instead of displaying a single unexplained number.

\section{Core Web Technologies}
The project uses a TypeScript monorepo with React and Vite for the frontend and Fastify for the API. PostgreSQL/PostGIS stores weather, location, and route-related data, while Redis supports short-lived caching and usage limits \cite{redis2024}. A background worker obtains and normalizes provider data so that the API can serve the web application without performing every external request during a page interaction.

The frontend is a single-page web application. React manages page and component state, while MapLibre GL \cite{maplibre2024} renders the interactive map, weather layers, route lines, and checkpoint markers. The main user-facing pages are the weather directory, location detail view, map, and route planner. Account settings, saved locations, saved routes, and plan limits support returning users.

Fastify \cite{fastify2024} exposes typed API endpoints for weather, forecasts, routes, risk assessments, accounts, and chat. Directus provides the administration and content-management services used by the application \cite{directus2024}. Shared TypeScript contracts keep the request and response shapes consistent between the frontend and backend. Docker Compose packages the web application, API, worker, database, and cache for local or server deployment.

\section{Supporting Assistant}
The conversational assistant is an optional interface for asking weather and travel questions. It uses a small set of allowlisted operations, such as location search, current weather lookup, forecast lookup, risk assessment, and route evaluation. The optional Gemini integration is treated as a language interface over these backend tools rather than as an independent source of weather facts \cite{googleFunctionCalling}. The backend executes these operations and returns the resulting data and citations to the interface.

The assistant complements the map, weather pages, and route planner; it does not replace them. The core application remains usable without a conversational model, and responses must indicate when evidence is missing or unavailable.

Administrators maintain accounts, monitor data services, and publish official alerts. \section{Overview of the System Architecture}
At context level, VietForecast contains a browser client, an application API, persistent and background services, and external providers. The browser presents the weather directory, map, route planner, account pages, and optional assistant. The API validates requests and coordinates weather lookup, routing, risk assessment, saved data, and chat operations. PostgreSQL/PostGIS stores application and spatial data, Redis supports short-lived caching and limits, and a worker normalizes provider data. Weather and routing providers supply external observations, forecasts, and road geometry. The diagram defines these boundaries; detailed components and deployment are described in Chapters~3 and~4.
